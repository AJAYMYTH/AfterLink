Why AfterLink exists

Real-time is easy to demo — and expensive to ship

Every product eventually needs the same eight things: push, presence, delivery confirmation, retries, reconnects, validation, typed errors and observability. Each common transport forces a choice between “too heavy” and “too bare”.

🧾

HTTP wasn’t built for streams

A REST call drags 200–800 bytes of headers for a 30-byte message, and servers can’t initiate — so clients poll. Polling burns bandwidth and battery, and adds latency exactly where it hurts.

🔌

Raw WebSockets stop at the pipe

You get a byte stream. Message framing, correlation IDs, routes, schema validation, error types, pub/sub, heartbeats and reconnects are all still ahead of you — in every project, rebuilt from scratch.

🧰

gRPC and MQTT bring an ecosystem

Proto codegen, browser proxies, brokers to operate. Excellent at scale — heavy for an app that just needs reliable real-time between a handful of services and clients.

🐢

Socket.IO trades speed for ease

The easiest start — and the slowest wire. JSON framing adds overhead to every message: about 10k msg/s in benchmarks, versus 30k+ for AfterLink.

The gap: nothing small, binary, schema-aware and browser-friendly out of the box. AfterLink’s answer: put the missing features in the protocol itself — routes, validation, typed errors, pub/sub, sessions — so no team has to rebuild them again.

What it is

One connection. The whole real-time toolbox.

AfterLink is an application protocol over TCP or WebSocket: compact binary frames, request/response routing, pub/sub topics, sessions with version negotiation, and typed errors — with SDKs for Node.js, the browser, Python and Dart.

📦 10-byte → 16-byte frames

Compact binary headers. v2 adds a version byte, priority and routing keys; v1 stays as the universal fallback.

🛣️ Routes + middleware

server.on('chat.send', handler) — three lines to a typed RPC endpoint, with middleware for auth, logging and rate limits.

✅ Schema validation built in

Attach a zod schema to a route. Bad payloads become typed VALIDATION_ERROR frames before your handler runs. Try it in the playground.

🚨 A shared error taxonomy

Canonical error codes travel on the wire; Node, Python, Dart and Browser SDKs all raise the same typed classes.

📣 Pub/sub in the protocol

Topics, subscribe/publish frames, server-side fan-out. The messaging demo below is literally the chat.lobby topic.

🔁 Sessions, reconnects, keep-alive

HELLO/HELLO_ACK establishes a session; clients auto-reconnect with backoff; PING/PONG keeps NATs open.

🔐 Security & operations

TLS transport, JWT auth on HELLO, per-connection rate limiting, graceful shutdown and health endpoints.

🧩 One protocol, four SDKs

Node.js, Browser (via the WebSocket bridge), Python and Dart speak the same bytes — verified by cross-SDK end-to-end tests.

How it works

Watch a session agree on a dialect — then look inside a frame

1 · The handshake (interactive — press play)

—

Press play to step through the handshake

Five frames take a fresh connection from “raw socket” to “AL/2 session”: HELLO → sniff → HELLO_ACK → ready. The client in the playground below did exactly this when this page loaded.

Backwards compatibility is the trick: HELLO always travels with the old 10-byte v1 header, so even servers shipped before AL/2 existed can parse it. v2-capable servers answer with accepted_protocol: 'v2'; v1-only servers simply don’t — and the client stays on v1 without noticing anything changed. Both fallback paths are covered by tests.

Challenges

What building it actually took

A protocol only counts if every SDK emits byte-identical frames. These are real problems from the changelog — each one now has a test that would catch it again.

4 SDKswire format

One wire format, four runtimes

Problem — Node, Python, Dart and the browser must agree on every byte.

What happened — Python packed an 18-byte v2 header (an extra reserved field) while Node and Dart packed 16 — cross-SDK tests failed on frame length.

Fix — one shared protocol-vector fixture that every SDK must decode and re-encode identically, enforced in CI.

AL/2compatibility

Changing the header under live traffic

Problem — v2 grew the header from 10 to 16 bytes. A v1 decoder reading a v2 frame would misread lengths and corrupt the stream.

Fix — negotiation, not breaking changes: HELLO stays v1-framed, servers sniff byte 2 (0x02 = AL/2), HELLO_ACK carries accepted_protocol, and each session’s framing is fixed independently.

Proof — fallback paths are tested: legacy v1 ACK, v1-framed v2 stub (like the Python bridge), and clients pinned to v1.

errorsPythonDart

One error taxonomy, three languages

Problem — Node raised typed classes for everything; Python and Dart raised generic errors with different shapes — the same failure looked different in each SDK.

Fix — canonical string codes travel on the wire (ROUTE_NOT_FOUND, VALIDATION_ERROR, INTERNAL_SERVER_ERROR…); every SDK maps them back to the same typed classes.

Dartmsgpack

MsgPack maps that Dart refused

Problem — Dart’s msgpack decodes into Map<dynamic, dynamic>, which crashes every Map<String, dynamic> call-site.

Fix — recursively normalize decoded maps at the client boundary. One test now covers nested message payloads end to end.

testingCI

Trusting bytes you can’t click

Problem — you can’t eyeball a 16-byte header, and “looks fine on my machine” doesn’t survive a mixed fleet.

Fix — the suite checks raw wire bytes: 138 JS tests including raw-socket negotiation, cross-SDK E2E (Node ↔ Python ↔ Dart), and hex dumps asserting exact headers like 10 00 02 03 …. If a byte moves, CI notices.

Real world

Where you’d actually use it

💬 Chat & collaboration

Rooms, typing indicators, presence and delivery receipts over topics — exactly what this page runs.

🎮 Multiplayer & games

Low-latency state sync and server-authoritative events, with priority flags in v2 for time-critical frames.

📈 Fintech & trading

Tick feeds and order events over one authenticated connection; typed errors for risk-check rejections.

📡 IoT & telemetry

Many tiny messages love tiny headers — and v2 routing keys split device fleets apart on the broker.

📊 Live dashboards

Subscribe once per widget; the server pushes — no polling loop, no cache-busting, no stale charts.

🧱 Service-to-service

Internal RPC with schemas and middleware, without REST glue code or a proto toolchain.

The same route, four SDKs

server.jsNode.js
const { Server } = require('@afterlink/server');

const server = new Server({ port: 4000 });

server.on('chat.send', async (req, res) => {
  // Fan out to everyone subscribed to the room
  server.publish('chat.lobby', {
    user: req.body.user,
    text: req.body.text,
  });
  res.send({ delivered: true });
});

await server.listen();
// → afterlink://localhost:4000  ·  health at /__health
browser-app.jsBrowser SDK — this page uses the same client
import { Client } from '@afterlink/browser';

const client = new Client('ws://localhost:4001/ws');

await client.connect();                     // HELLO → AL/2 negotiated
console.log(client.getProtocolVersion());   // 2

await client.subscribe('chat.lobby', (msg) => {
  console.log(msg.user, ':', msg.text);
});

await client.request('chat.send', { user: 'alice', text: 'hello!' });
chat.pyPython SDK
import asyncio
from afterlink import Client

async def main():
    client = Client("tcp://localhost:4000")
    await client.connect()
    print(f"protocol v{client.version}")          # 2

    await client.subscribe("chat.lobby", lambda m: print(m))
    await client.request("chat.send", {"user": "alice", "text": "hello!"})
    await client.disconnect()

asyncio.run(main())
chat.dartDart SDK
import 'package:afterlink/afterlink.dart';

Future<void> main() async {
  final client = AfterLinkClient(url: 'tcp://localhost:4000');
  await client.connect();
  print('protocol v${client.version}');        // 2

  client.subscribe('chat.lobby', (msg) => print(msg));
  await client.request<Map<String, dynamic>>(
    'chat.send', {'user': 'alice', 'text': 'hello!'},
  );
}

Shipping it for real

🔐 Security

  • TLS transport (afterlinks://) with certificate options
  • JWT auth carried in the HELLO payload
  • Per-connection rate limiting, enforced before handlers run

🛰️ Operations

  • Health endpoints: /__health, /live, /ready
  • Graceful shutdown — the server drains and tells clients why
  • Cluster mode with a Redis adapter for multi-node pub/sub
  • Compression thresholds for large payloads (zlib / brotli)
