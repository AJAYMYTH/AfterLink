Features

Replace HTTP, WebSockets, and gRPC with one protocol

AfterLink is 76% faster than WebSocket, with 90% less overhead — built-in pub/sub, schema validation, CLI tools, and browser support.

Binary Protocol

10-byte frame header with MessagePack serialization. 90% smaller than HTTP headers.

Request/Response

RPC-style calls with automatic correlation via message IDs. Multiplex hundreds of requests over one connection.

Built-in Pub/Sub

Subscribe to topics and broadcast messages over the same TCP connection. No WebSockets needed.

Schema Validation

Automatic Zod validation on every request. Invalid payloads rejected before your handler runs.

Auto-Reconnect

Clients recover from network drops automatically with configurable retry strategies.

Backend-Agnostic

Works with Supabase, InsForge, Firebase, AWS, MongoDB, or any backend you choose.

Streaming

First-class streaming API with STREAM_START, DATA, and END frames for chunked data.

CLI Tooling

Built-in afterlink CLI for testing routes, inspecting frames, and monitoring servers live.

Error Taxonomy

29 typed error classes with fromError() and fromFramePayload() for precise debugging.

Health Monitoring

Built-in /__health endpoint with liveness, readiness, and stats probes for load balancers.

TypeScript Ready

Full .d.ts type definitions for all packages — autocomplete and type safety out of the box.

Architecture

How AfterLink Works

From connection to response in four simple steps.

1

Connect

Client opens TCP socket and performs HELLO handshake with server.

2

Route

Client sends a REQUEST frame with the route name and payload.

3

Validate

Server automatically runs Zod schema check on the payload.

4

Respond

Server sends RESPONSE frame or publishes to a Pub/Sub topic.

// Connection Lifecycle
Client ─── TCP Connect ───▶ Server
Client ─── HELLO Frame ───▶ Server
Server ◀── HELLO_ACK ─── Client
Both ◀──▶ REQUEST / RESPONSE frames
Both ◀──▶ PUBLISH / SUBSCRIBE frames
Both ◀──▶ PING / PONG keep-alive
Client ─── CLOSE Frame ───▶ Server
Server ◀── CLOSE_ACK ─── Client

Quick Start

Hello World in 5 minutes

Build your first AfterLink server and client.

1

Create the Server

server.js
const { Server } = require('@afterlink/server');

const server = new Server({ port: 4000 });

server.on('ping', async (req, res) => {
  res.send({ message: 'pong', timestamp: Date.now() });
});

server.listen();
console.log('Server running on port 4000');
2

Create the Client

client.js
const { Client } = require('@afterlink/client');

async function main() {
  const client = new Client('afterlink://localhost:4000');
  await client.connect();

  const result = await client.request('ping', {});
  console.log(result);
  // { message: 'pong', timestamp: 1748000000000 }

  await client.disconnect();
}

main();
3

Run It

Terminal
# Terminal 1 - Start server
$ node server.js

# Terminal 2 - Run client
$ node client.js

# Output:
# { message: 'pong', timestamp: 1748000000000 }

Troubleshooting

Common Issues

Solutions to frequently encountered problems.

Ensure the server is running and no other process is using port 4000. Check with netstat -ano | findstr 4000 on Windows or lsof -i :4000 on macOS/Linux.

Verify your JWT secret matches between client and server. Ensure the token hasn't expired. Check server logs for detailed error messages.

The server rejects payloads that don't match the Zod schema. Check the error response for the specific field that failed validation. Use z.any() for optional fields.

Windows firewall may be blocking the connection. Add an inbound rule for Node.js or run as administrator. Also check antivirus settings.

Each idle connection uses ~50KB. Set maxConnections in server options. Enable keep-alive timeout to close inactive connections.

Ensure both client and server are configured for TLS. Verify certificate paths and that the CA is trusted. Use rejectUnauthorized: false only for testing.

AfterLink doesn't guarantee ordering across topics. Messages within the same topic are ordered. Use sequence numbers if strict ordering is required.
